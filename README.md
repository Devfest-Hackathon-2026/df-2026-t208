# なぞまちワールド（NAZOMACHI WORLD）— MVP Webアプリ

**「地球の全部が、事件現場になる。」**

DevFest GDGoC Japan Hackathon 2026 / チーム みらいクラフト（DF-2026-T208・大阪会場）
カテゴリ： Entertainment（主）× Tourism（副）

場所を選ぶと、その場所でしか起きないミステリー（事件）が始まる探索ゲームです。実在のスポットを巡って手がかりを集め、AIゲームマスターの段階ヒントで詰みを防ぎ、犯人とトリックを推理。解決編では「その街の本当の話」が明かされ、遊びが観光と学びにつながります。

## 遊び方（画面の流れ）

1. **場所選択**：プリセット3拠点（大阪・梅田／京都・祇園／東京・浅草）＋テーマ選択（探偵もの／学園もの／ホラー風。テーマで導入の語り口が変わります）
2. **事件発生**：場所ごとに完成した事件シナリオを表示（導入文・実在スポット5件・手がかり・容疑者3名・真相を事前生成データとして埋め込み）
3. **捜査**：Google Maps Embed（キー不要形式）で現場を表示し、スポットを選んで「調べる」と手がかりを収集（進捗バー表示）
4. **AIゲームマスター**：チャット風UIで段階ヒント（Lv.1〜3）を提示し、「詰んで終わる」を防ぐ
5. **推理**：容疑者選択＋トリック選択の2問。正解で解決編へ、不正解でもGMのフォロー付きで再挑戦可能
6. **解決編**：真相＋「街の本当の話」＋結果シェア（URLパラメータ `?case=...&theme=...&result=solved` のリンク生成とコピーボタン。リンクを開くとバナーが出て同じ事件に挑戦できます）

## MVPのスコープ（Gemini設計批評ループ Round 1 の線引きを採用）

| 項目 | MVPでの扱い | 理由（Own the Why） |
|---|---|---|
| おうちモード（Street View捜査） | **採用（核）** | 屋内・審査会場でも安定して体験できる |
| まちモード（GPSチェックイン） | **切る → 次期ロードマップへ分離** | 屋外検証リスクの排除と審査体験の安定化のため。二兎を追って核の磨き込みが犠牲になるのを避ける（アプリ内の「今後のロードマップ」にも明記） |
| 場所選択 | **3拠点の選択式のみ**（自由入力なし） | 実在しないスポットや手がかりのハルシネーションを防ぎ、実在性を担保する |
| 事件シナリオ | **全シナリオ事前生成＝即時表示**（生成待ち時間ゼロ） | リアルタイム生成は30秒〜1分以上の沈黙になりデモで致命的。GM判定（推理の正誤フォロー）のみルールベースで即時処理 |
| 手がかりの設計 | **スポット到達（選択して調べる）で得られる** | Street Viewは道路視点のみ・画質にムラがあるため、実写の細かい文字を読ませる手がかりにはしない |
| シェア | **URLパラメータ方式**（DB・認証なし） | Firebaseは共有URLの受け皿（静的ホスティング）に絞り、アカウント管理を持たない |

## 収録シナリオ

| 場所 | 事件名 | 概要 |
|---|---|---|
| 大阪・梅田 | 梅田迷宮と消えた水時計の設計図 | 水時計の制御基盤データが抜き取られ、断片が梅田の5スポットに分散隠蔽。犯人は保守担当エンジニア水木麗子（Gemini設計ループ Round 1 で生成されたシナリオを採用） |
| 京都・祇園 | 消えた花簪（かんざし） | 発表会前夜に桜の簪が桐箱ごと消失。真相は祇園に客を呼び戻すための狂言盗難 |
| 東京・浅草 | 提灯に消えた設計図 | 大提灯の設計図の写しが準備室から消失。見習い職人が改良メモを認めてほしくて提灯内部に隠していた |

いずれも実在のスポット名・実在の豆知識（歴史・名物）を土台にし、捏造を避けて構成しています。

## 動かし方

ビルド不要・依存なしの静的サイトです。

- **そのまま開く**：`index.html` をブラウザで開く（地図表示にはインターネット接続が必要です）
- **ローカルサーバー**：このフォルダで `python3 -m http.server 8000` → http://localhost:8000
- **Firebase Hosting へデプロイ**：
  1. `.firebaserc` の `YOUR_FIREBASE_PROJECT_ID` を実際のプロジェクトIDに書き換える
  2. `firebase deploy --only hosting`（`firebase.json` の `public: "."` でこのフォルダ全体＝`assets/` のキービジュアル含む、が公開されます）

## コスト方針（追加費用ゼロ）

本MVPは**追加費用ゼロ**で運用できる構成に固定しています。

- Firebase は無料の **Spark プラン**の範囲のみを使う（Blaze へのアップグレードはしない）
- 課金アカウントが必要なサービス（Cloud Run 等）と有料 API キー（Places API／Maps JavaScript API／Gemini API の有料利用）は使わない
- 地図表示はキー不要の埋め込み（`maps.google.com/maps?q=...&output=embed`）のみ
- シナリオは全て事前生成してアプリに同梱するため、生成 API の呼び出し自体が発生しない

## 技術構成と「なぜその技術か／捨てた代替案」（コンセプト §4 より）

| 技術 | 役割 | なぜこれでないとダメか |
|---|---|---|
| Street View | 事件の舞台（実写の街） | 世界中の実在景観が撮影済み。「舞台を作る」のではなく「発見する」から成立する。過去画像まで持つ同等の資産は他にない |
| Places API | 実在スポットの名前・カテゴリ・評価 | 事件の舞台を実在の店や施設に限定し、実在しない場所を捏造させないための土台 |
| Gemini（マルチモーダル） | 景観画像からの手がかり抽出／事件の物語生成／GM対話 | 「画像の意味づけ」「物語」「対話」の3役を1つのモデルで担う必要がある |
| Maps JavaScript API | 探索 UI | Street View と地図の連動表示 |
| Cloud Run | 生成バックエンド | API キーを表に出さない。生成結果のキャッシュで速度とコストを安定させる |
| Firebase | 事件データ・進行状況・シェア | シェアリンクで友だちが同じ事件を遊べるようにする |

**検討した代替案と、落とした理由（Own the Why）**

- 人間が街ごとにコンテンツ制作 → 品質は高いが、街の数だけコストがかかり拡張しない
- 自前で写真を撮って使う → 撮影済みの場所でしか遊べず、「世界中」が消える
- テキストだけで物語生成（画像なし）→ 「実在の場所で事件が起きている」感覚＝このプロダクトの命が消える

### MVP実装と本番構想の対応

| 対象 | MVP（本アプリ） | 本番構想 |
|---|---|---|
| 事件生成 | Geminiとの設計ループで生成・検証したシナリオを事前生成データとして同梱（即時表示） | Gemini が Places API の実在スポットから動的生成し、Cloud Run でキャッシュ |
| 地図・舞台表示 | キー不要の Google Maps Embed（`maps.google.com/maps?q=...&output=embed`） | Maps JavaScript API + Street View の連動表示 |
| GM対話 | ルールベースの段階ヒント（Lv.1〜3）＋推理の正誤フォロー | Gemini による自由対話型GM |
| シェア | URLパラメータで事件と結果を共有 | Firebase に事件データを保存し、同じ事件を再現可能に |

> 本MVPは APIキーを一切含まず、外部APIも叩きません（地図の埋め込み表示を除く）。完全スタンドアロンで動作します。

## 審査8項目への対応メモ

| 観点 | 本MVPでの対応 |
|---|---|
| 課題設定の妥当性 | 観光コンテンツ制作コストの高さ→有名地への一極集中（オーバーツーリズム）と、移動困難な人へ旅体験が届かない問題を提示。体験の制作コストをゼロにする解決策として設計 |
| Google技術の活用度 | Street View／Maps Embed を舞台に、Gemini との設計ループでシナリオを生成・批評・改訂（梅田編はGemini生成を採用）。本番構想は Places API／Cloud Run／Firebase まで §4 の通り接続 |
| プロダクトの品質・完成度 | 3事件すべて導入→捜査→推理→解決編まで完結して遊べる。事前生成で待ち時間ゼロ、不正解でも詰まない設計 |
| UI/UX | 「地図（場所）」と「物語（文章）」の2層に絞った一本道UI。進捗バー、段階ヒント、スマホ対応 |
| 社会的インパクト | 観光分散（無名の街にも「行く理由」）、おうちモードによるアクセシビリティ、自治体・商店街が公式コンテンツを配れる将来像 |
| 独創性 | GeoGuessr が場所を「当てる」ゲームなら、本作は場所で「物語が起きる」ゲーム。解決編で実在の街の知識が残る仕掛け |
| 拡張性・保守性 | 生成パイプライン（場所データ取得→手がかり抽出→物語生成→検証）の分離構想。MVPもシナリオデータ追加だけで拠点を増やせるデータ駆動構造 |
| セキュリティ・検証可能性 | APIキー不使用、位置情報を保存しない設計。舞台は実在スポットのみに限定し、実在する手がかりかの検証工程を設計に明記 |
