# プロダクト説明ドキュメント — なぞまちワールド（NAZOMACHI WORLD）

チーム： みらいクラフト（受付番号 DF-2026-T208・大阪会場）
カテゴリ： Entertainment（主）× Tourism（副）
公開URL： https://nazomachi-world-a3598.web.app
GitHub： https://github.com/Devfest-Hackathon-2026/df-2026-t208

## 1. Why — 解決する課題

街歩き体験や観光コンテンツは「作るコスト」が高すぎて、有名観光地にしか存在しません。日本のほとんどの街は「行っても何も起きない場所」のまま素通りされ、観光は有名地に一極集中します（オーバーツーリズム）。混雑する側も、素通りされる側も不幸です。さらに、体調・お金・距離の理由で移動が難しい人には「旅の体験」そのものが届きません。

なぞまちワールドは、体験の制作コストをAIでゼロにすることで、どの街にも、その人だけの物語を届けます。

## 2. プロダクト概要

場所を選ぶと、**その場所でしか起きないミステリー（事件）**が生成される探索ゲームです。

- **おうちモード**：Street View の実写の中を歩いて捜査する。世界中、どこでも遊べる
- 舞台は実在の場所、手がかりになるのは実在のスポット。事件は毎回 AI が生成

遊びの流れ：
1. 行き先の街を入力すると、その街専用の事件がその場で生成される（事件生成エンジン）。監修済みの事件ファイルから選ぶこともできる。事件の詳細画面で、語り口（探偵もの／学園もの／ホラー風）を選ぶ
2. 事件が発生：導入文、舞台になる実在スポット5件、手がかり、容疑者、真相
3. Street View（埋め込み地図）を見ながらスポットを巡り、手がかりを集める
4. 詰まったら AI ゲームマスター（GM）に相談。ヒントは段階的に出るので誰でも最後まで到達できる
5. 犯人とトリックの両方を推理して回答する
6. 解決編：真相と一緒に「その街の本当の話」（実在の歴史・名物・店の素顔）が明かされる
7. 結果をリンクでシェア → 友だちも同じ事件に挑戦できる

収録事件（MVP）：大阪・梅田『梅田迷宮と消えた水時計の設計図』／京都・祇園『消えた花簪』／東京・浅草『提灯に消えた設計図』。各事件5スポット・容疑者3名・解決編付き。

**事件生成エンジン（本プロダクトの核）**：任意の行き先（市区町村名など）を入力すると、その街専用の事件をその場で生成する。物語の型（職人の設計図／祭りの宝物／時計台の制御データ／老舗のレシピ／橋の原版／商店街の原画の6系統）×実在スポットの型（駅前・商店街・社寺・橋・市場・公園・資料館・史跡・港・展望の10種）×容疑者・トリック・手がかりの連鎖を、行き先の名前をシードにして決定的に組み立てる（同じ行き先からは同じ事件が生まれ、URL共有や再訪でもブレない）。捜査画面の地図（Google Maps埋め込み）には実際のその街が表示され、生成されたスポット名で実在の場所が舞台になる。「有名地にしかコンテンツが存在しない」という課題に対し、用意した事件だけでなく、どの街にもその場で事件を届けられることが本プロダクトの新規性である。

## 3. 技術選定と「なぜそれか」／捨てた案とのトレードオフ（Own the Why）

| 技術・判断 | 役割／なぜこれでないとダメか | 捨てた代替案と理由 |
|---|---|---|
| Street View | 事件の舞台（実写の街）。世界中の実在景観が撮影済みで「舞台を作る」のではなく「発見する」から成立する。過去画像まで持つ同等の資産は他にない | 自前で写真を撮って使う → 撮影済みの場所でしか遊べず「世界中」が消える |
| 事前生成シナリオ（アプリ同梱） | デモでの待ち時間ゼロ。品質を人間が事前に検証できる。生成APIコストもゼロ | 完全リアルタイム生成 → 1事件30秒〜1分以上の沈黙が審査の場で発生し、品質も未検証になる（Gemini設計批評ループで指摘を受けて切替） |
| Gemini（設計ループ＋シナリオ生成） | 「物語生成」「土地の実話の織り込み」「設計批評」の3役を担う。梅田編のシナリオとキービジュアルのプロンプトはGemini生成を採用 | 人間だけの執筆 → 街の数だけコストがかかり、本プロダクトの核（制作コストゼロ）と矛盾 |
| 実在スポットへの固定（選択式3拠点） | 舞台スポットと解決編の事実は全て実在のものに限定し、捏造を防ぐ土台 | 完全自由入力の場所選択 → 存在しない場所のハルシネーションとプロンプト破綻を招くためデモでは選択式に絞った |
| Firebase Hosting（Spark・無料枠） | Google実行基盤の要件を満たす。バックエンドなしMVPには静的ホスティングで十分で、運用コストゼロ | Cloud Run バックエンド → 課金アカウントが必須で、事前生成アーキテクチャでは不要 |
| キー不要の Maps 埋め込み | APIキーなしで地図表示。キー漏洩・課金リスクがない | Maps JavaScript API（キー発行） → MVPの表示要件に対して過剰 |
| まちモード（GPSチェックイン）を今回は実装しない | 屋内審査会場からのGPS実機検証（ジオフェンス半径・ドリフト対策）はリスクが高く、核である「ミステリー生成と推理体験」の磨き込みを犠牲にするため。次期ロードマップへ分離し、アプリ内にも明記 | 両モード同時実装 → 二兎追いで共倒れのリスク |

本番構想：Cloud Run に生成バックエンドを置き（APIキーはサーバー側のみ）、Places API で実在スポットの裏付けを取り、Gemini のオンデマンド生成＋キャッシュで世界中の街に対応。Firebase（Firestore）で事件データとシェアを管理し、まちモード（GPS）を追加する。

## 4. 品質・設計の方針

- **UI/UX**：画面は「地図（場所）」と「物語（文章）」の2層だけ。一本道で謎解き初心者でも迷わない
- **事件生成エンジン（核機能として実装）**：行き先を入力すると、その街専用の事件（5スポット・容疑者3名・真相・段階ヒント・解決編まで完結）を即時生成する。生成は端末内で完結し待ち時間もAPIコストもゼロ。同じ行き先からは同じ事件が再現される決定的生成のため、生成結果をそのまま事件ファイルとして棚に並べ、詳細・捜査・推理の全フローで監修済み事件と同等に扱える
- **発見のUI/UX（v4で再構築）**：ファーストビューは「フォームと一覧の管理画面」ではなく、実在の探索ゲーム（Questo等の強豪）の文法に倣い、キービジュアル全面のヒーローから始まる。行き先入力はピル型でヒーロー内に埋め込み、例示チップで入力なしでも生成を試せる。事件カードは台帳型をやめ、実在の街の実写・生成画を使ったポスター型（画像フルブリード＋タイトル＋メタ1行）に統一し、検索と探し方の軸（場所／時間／雰囲気／難易度）は「もっと探す」に集約して開いた瞬間の情報量を絞った。詳細画面では事件概要に加えて実際の舞台のGoogle Maps埋め込みを表示し、「シナリオ設計： Gemini」のクレジットリボンや結果画面の奥付など、Google技術の使用箇所をプロダクト内でも明示している。生成した事件は端末に保存され、再読み込み後も棚に残る
- **詰み防止**：GMの段階ヒント（Lv.1〜3）で誰でも解決編に到達できる
- **セキュリティ**：APIキーを一切持たない。アカウントも作らない
- **生成の検証**：舞台は実在スポットのみ。解決編では「事件のフィクション」と「街の本当の話」を分けて提示する

## 5. 社会的インパクト

- **観光分散**：無名の街にも「行く理由」が生まれ、有名地への一極集中をほぐす
- **地方の側の道具になる**：将来は自治体や商店街が、自分たちの街の事件を公式コンテンツとして配れる
- **アクセシビリティ**：おうちモードで、移動できない人も世界中を「歩いて旅する」体験ができる

## 6. 先行事例との違い

- GeoGuessr は場所を「当てる」ゲーム。なぞまちワールドは場所で「物語が起きる」ゲーム
- 一般的な謎解きコンテンツは人間が場所ごとに制作するため有名地にしか存在しない。本プロダクトは生成コストをゼロにし、実在の街そのものを無限の舞台にする

## 7. 開発プロセス

Muse（統括・実装・検証）と Gemini（設計批評・スコープ線引き・梅田シナリオ・キービジュアルプロンプト）によるAI同士の批評ループで「案を出す→批評する→磨く」を回し、チーム（人間3名）がプロダクト決定と最終判断を行った。Google のコーディングエージェント Jules も評価したが、本リポジトリが組織配下でオーナー承認が必要だったため今回は採用せず、その経緯も含めて記録している。
