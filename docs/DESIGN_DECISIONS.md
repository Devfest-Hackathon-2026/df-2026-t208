# 設計判断の記録 — なぞまちワールド（NAZOMACHI WORLD）

チーム： みらいクラフト（DF-2026-T208）／カテゴリ： Entertainment（主）× Tourism（副）
公開URL： https://nazomachi-world-a3598.web.app

この文書は、公式テーマ「Own the Why, Build with Intent.」に応えるための記録である。何を作ったかだけでなく、**なぜその選択をしたか、他の選択肢と比べて何を捨てたか**を残す。

## 1. 企画のWhy — 誰の、どんな課題か

**課題**：街歩き・観光コンテンツは有名地に偏在している。梅田・祇園・浅草のような名所には謎解きやガイドが溢れる一方で、無名の街には「その街を歩く理由」になるコンテンツが存在しない。同時に有名地はオーバーツーリズムに悩んでいる。

**着眼**：もし「行き先を決めるだけで、その街専用の事件（謎解き）がその場で生まれる」なら、コンテンツの供給側の制約（街ごとに作り込むコスト）が消える。観光の分散と、無名の街の発見可能性を、同じ仕組みで解ける。

**プロダクト**：行き先の街名を入力すると、その街専用の謎解き事件が生成される探索ゲーム。監修済みの事件（大阪・梅田／京都・祇園／東京・浅草）も用意し、生成の品質の物差しとした。

## 2. 構成の判断

| 層 | 内容 | なぜこの形か |
|---|---|---|
| 事件生成エンジン | 物語の型6系統×スポットの型10種×容疑者・トリック・手がかり連鎖を、街名をシードに決定的生成 | 「どの街にも届く」が企画の核。生成がブレると共有・再訪・推理の公平性が崩れるため決定的方式にした |
| 監修事件（3件） | Geminiと設計した本格シナリオ。各5スポット・3容疑者・真相＋「街の本当の話」 | 生成だけでは品質の天井が見えない。手作りの到達点を示し、生成の評価基準にするため |
| 発見レイヤー | ポスター型カード棚＋検索＋4つの探し方の軸（場所／時間／雰囲気／難易度） | 事件が増えても「次に遊ぶ1件」に迷わないため。ただしファーストビューでは生成を主役にし、発見UIは後段に下げた（§5） |
| プレイループ | 詳細→導入→捜査（地図＋スポット＋GM）→推理→結果（ランク＋シェア） | 謎解き初心者が一本道で完走できる長さ（約10〜15分）に収めるため |

## 3. 技術選定とトレードオフ

- **生成方式： 端末内（オンデバイス）決定的生成を採用。** Gemini APIのライブ生成は採らなかった。理由は3つ。(1) 課金：本チームは追加出費ゼロを絶対条件とした（GCPクレジットの利用で前払いを求められる事象も実際に発生し、運営へ確認した）。(2) 再現性：同じ街からは同じ事件が生まれることが、URL共有・再訪・推理の公平性に必須。(3) 速度と安定性：API待ちなし・オフラインでも遊べる。代償として生成スポットは「型」の名前（例：◯◯の商店街）になる。本番構想では Gemini＋Places API で実在スポット名と実話に差し替える設計をプロダクト資料に明記した。
- **ホスティング： Firebase Hosting（Spark無料枠）。** 大会ルール「Googleの実行基盤で公開しRegional Dayまで維持」に適合し、無料枠で完結する。
- **地図： Google Maps埋め込み（output=embed）を採用。** Places APIはキー管理と課金の検討が必要なため見送り、監修事件では実在スポット名をシナリオ側で担保した。埋め込みの弱点（スクロール干渉＝マップトラップ）は、捜査画面では「操作トグル式」、詳細画面では表示専用にして対策した。
- **実装： フレームワークなし（バニラHTML/CSS/JS）。** 依存ゼロで軽く、どの環境でも同じに動く。状態は localStorage（生成した街・解決済み・言語）に保存する。
- **多言語： 翻訳データを `i18n-data.js` に分離。** UI・監修3事件・生成キットを日英両対応し、コードと翻訳を分けて保守できるようにした。訪日観光客がそのまま遊べることが Tourism カテゴリの訴求になる。

## 4. Google技術の使い方（審査項目への対応）

- **Gemini**：監修3事件のシナリオ設計（プロダクト内にも「シナリオ設計： Gemini」と明示）。あわせてデザイン批評ループの批評役。
- **Google Maps**：捜査の舞台そのもの。詳細画面と捜査画面に実在の街の地図を表示し、生成事件でも実際の街が舞台になる。
- **Firebase Hosting**：公開基盤。

## 5. デザインの変遷 — 批評ループの記録

完成形は一発では出ていない。代表（人間）の実機フィードバック、Geminiの批評、独立したClaudeの監査、競合調査（Questo／SCRAP／Actionbound）を回し、各ラウンドで捨てたものが今の形を作った。

- **v1〜v3**：駅名標モチーフのデザインシステムを確立。しかしホームが「フォーム＋台帳カード」で、実機を見た代表から「会社の管理画面みたい」と却下された。
- **v4**：競合調査と2方向のAI批評が同じ結論（ヒーローがない・フォームが露出・台帳文法）に収束したため、ファーストビューを全面刷新。キービジュアル全面のヒーロー＋ピル型生成入力、ポスター型カード、発見UIの後段化、Google技術の可視化（Maps埋め込み・Geminiリボン・結果の奥付）。あわせて、端末キャッシュによる表示崩れを防ぐキャッシュバスティングを導入。
- **v5**：批評ラウンド4（Gemini＋Claude監査、計30件の指摘）から実装したもの — 遊び方の3コマ図解新設、開始ボタンと進捗のsticky化、詳細のメタチップ化、GM挨拶の二重再生の解消、推理手帳の既定オープン、結果画面のシェア前倒しとOS共有対応、マップトラップ対策、再訪時スプラッシュ省略、「Street View」表記と実物（Maps）の不一致の是正。英語対応もこの版で搭載。
- **v6**：代表の実機指摘「導入画面がまだAIっぽい／GMが文字だけ」を受け、GMのマスコットキャラクター（デフォルメ探偵）を制作してスプラッシュ・導入・推理に配置し、導入画面に事件のキービジュアルを追加。言語切替がタグラインに重なる問題も修正。「AIっぽさ」の正体は、無個性な部品の寄せ集めだと判断し、固有のキャラクターと絵の資産で置き換える方針を取った。

## 6. AIをどこで・なぜ使ったか（必須項目への回答）

- **Gemini**：(1) 監修シナリオの設計パートナー（物語の型と街の実話の組み立て）。(2) デザイン批評の批評役（アイデアと客観的批判は人間の身内ではないAIの方が率直なため）。
- **Claude**：実装と検証（コード生成、E2Eの自動テスト、デザイン監査の第二意見）。
- **画像生成AI**：キービジュアル、マスコットキャラクター。写真素材は実在の街の実写（出典は素材利用シートに明記）と使い分けた。
- **人間の役割**：企画の決定、実機での最終判断（「管理画面みたい」「AIっぽい」は人間の目でしか出なかった指摘）、提出判断。AI同士で「案を出す→批評する→磨く」ループを回し、人間は判断ポイントだけを見る運用にした。

## 7. 学んだこと

- 「動くもの」と「遊びたいもの」の距離は、機能ではなくファーストビューと手触りで決まる。同じ中身でも、管理画面の文法で包むと誰も遊ばない。
- AIに作らせるほど、判断の記録が価値になる。なぜ捨てたかを残すことが、次の改善と説明の両方に効いた。
- 決定的生成のような「地味な正しさ」（再現性・無料・速い）は、派手なAI機能よりプロダクトの信頼を支える。

## 8. 既知の限界と次の一手

- 生成スポットは型名称のため、本番では Gemini＋Places API で実在スポット名・実話・営業時間と接続する。
- 推理は2択形式。証拠スロット式など、集めた手がかりを使う推理UIへの発展余地がある。
- スコア（解決率）は表示用の目安値であり、実測ではない。公開版では実測に置き換える。
